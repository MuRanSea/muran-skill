8.4.1.4 多分块上传带 Trailing Header 的签名机制
在多分块上传时，TOS 支持在有效数据末尾以 Trailing Header 的形式携带有效数据的校验和。服务端会基于接收到的数据计算校验和，和 Trailing Header 中的校验和进行对比，以验证数据完整性。本文介绍使用 Trailing Header 和链式签名时的签名计算过程、签名示例等内容。

说明
Trailing Header 支持单独使用，如果单独使用，则不涉及本章的内容，详细介绍，请参见 Header签名概述。

函数名 功能描述
UriEncode()
对字符串进行编码，限制如下：
除了 A ~ Z 、 a ~ z 、
0 ~ 9 、 - 、 . 、 _ 、 ~ 字符，其他
字符都需要编码。
空格需要编码为 %20 （不支持编码为 
+ ）。
每个 URI 编码字节由 % 和两位十六进制数
组成。十六进制值必须是大写。
除了对象名中的 / 无需编码，其他情况下
的 / 都需要编码。
Lowercase() 将字符串转换成小写。
Hex() 16 进制编码。
SHA256Hash() SHA256 算法。
HMAC-SHA256() HmacSHA256 算法。
Trim() 删除字符串开头和结尾的空白符。

Content-Encoding
本场景下， Content-Encoding 值建议包含 toschunked 时，表示允许使用多分块的方式上传数据，需要配合 x-tos-content-sha256 使用。
说明
在保存对象时，TOS 不会将 toschunked 属性作为用户数据保存，下载
对象时也不会在 Content-Encoding 返回
tos-chunked 属性。
x-tos-trailer
表示 Trailing Header 中校验和使用的算法，取值
仅为 x-tos-hash-crc64ecma ，需要配合 x-toscontent-sha256 、 Content-Encoding: tos-chunked使用。
x-tos-decoded-content-length
用于服务端校验接收到的有效数据长度是否正
确。可选，设置为原始文件大小。
说明
设置 x-tos-decoded-content-length 值
时，不包含由多分块编码引入的格式数
据、签名数据、Trailing Header 数据的
长度。例如：要上传一个 4GB 的文件，
将值设置为 4294967296。
