6.4.4 使用 Webhook 接收事件通知
如果你需要把 Agent 运行结果接入审计、告警或内部编排系统，不必为每个资源持续轮询状态。配置Managed Agents Webhook 后，方舟会在 Agent、Environment、Session、Memory Store 和 Vault 等资源发生变化时主动回调你的服务端。本指南从创建接入点开始，串起接收服务、验签去重、测试事件、故障恢复、密钥轮换和资源清理。
选择接收方式
Webhook、SSE 和轮询解决的问题不同。需要监听多个资源的异步变化时，使用 Webhook。需要实时展示单个 Session 的消息、工具调用和增量输出时，使用 SSE。需要主动核对资源当前状态或补查 Session 历史事件时，调用对应的查询接口。
Webhook 支持订阅下表中的业务事件。事件正文结构详情请参见 Webhook 事件结构参考 。维度 Webhook SSE 轮询

判定 Session 运行结果
session.status_idled 只表示 Session 已进入空闲状态，不表示当前轮次正常结束。Webhook 事件不携带Session Event ID 或轮次 ID，不能只查询最近一条 session.status_idle 后自动推进业务。收到该通知后，按以下顺序判定结果：
从 Webhook 事件的 data.id 读取 Session ID，并按 Webhook 外层 id 去重。
找到业务侧记录的本轮边界。推荐在发送本轮 user.message 、 user.tool_result 或 user.tool_confirmation后，保存发送事件接口返回的事件 ID；如果接收端已经持续消费 Session 事件，也可以保存上一条已处理 Session Event 的 processed_at 作为水位。
查询历史事件：使用 Session ID 调用 查询会话事件列表 ，查询本轮边界之后的历史事件。可以用 created_at[gt] 缩小时间窗口，并按 processed_at 正序扫描；只有确认候选 session.status_idle 位于本轮边界之后，才将它作为本次通知对应的状态事件。
读取对应 session.status_idle 事件的 stop_reason.type ： 
end_turn ：当前轮次正常结束，可以处理业务结果。
requires_action ：当前轮次正在等待工具确认或工具结果，按 stop_reason.event_ids 继续处理。retries_exhausted ：当前轮次重试次数已用尽，不要按成功结果推进后续流程。
Webhook 可能早于 Session 历史事件完成同步，也可能延迟投递。若查询结果中只有本轮边界之前的 session.status_idle ，或无法确认候选事件与本轮业务任务的关系，等待后继续查询；不能仅凭最近一条 end_turn 推进业务。无法建立本轮边界时， session.status_idled 只适合作为状态核对信号，不适合驱动自动发布、扣款或外部通知等必须精确对应轮次的流程。
Webhook 外层 id 以 whe- 开头，只标识 Webhook 事件信封。Session 历史事件使用独立的事件 ID，不能将 whe- ID 传给 Session Events 查询接口。Session 事件字段详情请参见 会话事件结构参考 。准备接收端

def decode_signing_secret(value: str) -> bytes:
if not value.startswith("whsec_"):
raise ValueError("WEBHOOK_SIGNING_SECRET must start with whsec_")
 encoded_secret = value.removeprefix("whsec_")
 encoded_secret += "=" * (-len(encoded_secret) % 4)
try:
 secret = base64.b64decode(encoded_secret, validate=True)
except (binascii.Error, ValueError) as exc:
raise ValueError("WEBHOOK_SIGNING_SECRET contains invalid Base64 data") from excif len(secret) != 32:

return secret
def verify_signature(
 secret: bytes,
 webhook_id: str,
 timestamp: str,
 raw_body: bytes,
 signature_header: str,
) -> bool:
 signed_content = (
 webhook_id.encode("utf-8")
 + b"."
 + timestamp.encode("utf-8")
 + b"."
 + raw_body
 )
 digest = hmac.new(secret, signed_content, hashlib.sha256).digest()
 expected_signature = base64.b64encode(digest).decode("ascii")
 version, separator, signature = signature_header.partition(",")
return bool(
 separator
and version == "v1"
and hmac.compare_digest(signature, expected_signature)
 )

按以下顺序处理请求：
读取 webhook-id 、 webhook-timestamp 、 webhook-signature 和原始请求体。
将 webhook-timestamp 解析为 Unix 秒，并拒绝与服务端当前时间相差超过 5 分钟的请求。去掉 signing_secret 的 whsec_ 前缀，再对剩余内容进行 Base64 解码。解码结果必须为 32 字节。使用 webhook-id.timestamp.raw_body 计算 HMAC-SHA256 和 Base64 签名。
校验签名版本为 v1 ，并使用 hmac.compare_digest 等恒定时间比较函数比较 Base64 签名。验签通过后解析 JSON，并确认正文外层 id 与 webhook-id 相同。
按外层 id 去重。重复收到同一个 whe- ID 时，不要重复执行有副作用的业务操作。
可靠保存事件或业务处理结果后，返回 HTTP 2xx。
注意
不要先解析 JSON，再重新序列化正文参与验签。空格、字段顺序或转义方式变化都会改变字节序列，导致合法请求验签失败。
Python 示例使用内存集合去重，进程重启后记录会丢失。生产环境应在数据库或缓存中为事件 ID 建立唯一约束，并将去重记录的保留时间覆盖业务追溯周期。
投递和重试
业务事件不保证严格顺序或恰好一次投递。同一事件重试时， webhook-id 、 created_at 和原始正文保持不变。平台会为每次尝试重新生成 webhook-timestamp 和 webhook-signature 。
只在事件已经可靠入库或业务结果已经持久化后返回 2xx。需要异步处理时，先把事件写入内部队列，再返回 204。返回 3xx 不会让平台跟随重定向。

恢复自动停用
一个业务事件经过全部尝试后仍未成功，只计为一次最终投递失败。连续 20 个业务事件最终投递失败时，平台自动停用接入点，并将 disabled_reason 设为 consecutive_failures 。

回调地址返回 3xx， disabled_reason 为 redirect 。
回调地址未通过公网地址安全校验， disabled_reason 为 unsafe_url 。
HTTPS 证书或主机名校验失败， disabled_reason 为 invalid_certificate 。

在维护窗口轮换
本指南提供的 Python 接收端一次只读取一个 WEBHOOK_SIGNING_SECRET ，适合在维护窗口中轮换：停用 Webhook 接入点。停用会取消尚未开始和等待重试的投递，停用期间产生的事件不会在恢复后补发。
重置签名密钥：
保存响应中的新密钥，更新接收端的 WEBHOOK_SIGNING_SECRET ，然后重启接收服务。
发送测试事件并确认验签成功。测试事件在接入点停用期间也可以投递。
启用接入点，恢复业务事件投递。
通过 Webhook 事件查询和对应资源查询接口，核对维护窗口内的状态变化。
新密钥仅在本次成功响应中返回。关闭响应前，将新密钥写入密钥管理服务。
持续接收时轮换
需要持续接收业务通知时，不要直接使用“重置密钥后更新环境变量并重启”的顺序。先部署支持受控轮换的接收端，再执行以下步骤：
进入轮换模式：让接收端继续使用旧密钥验签；仅在本次受控窗口内，对无法验签的请求返回 HTTP503，使业务事件进入平台重试流程。
重置并保存新密钥：调用重置密钥接口并保存新密钥。
加载双密钥：在接收端原子加载新密钥，同时保留旧密钥。过渡期间使用新旧两个密钥依次验签，并继续按事件 ID 去重。
发送测试事件：确认新密钥验签成功。业务事件最多投递 3 次，应在重试次数用尽前完成新密钥加载。
移除旧密钥：保留旧密钥至少覆盖接收端允许的签名时间窗口；本指南示例为 5 分钟。随后移除旧密钥，并退出轮换模式。
警告
平台不会同时使用新旧密钥签名。接收端尚未加载新密钥时，新签名请求会使用旧密钥验签失败；接收端移除旧密钥后，已经发出的旧签名请求也会验签失败。只有在明确进入受控轮换模式后，才将暂时无法验签的请求返回 503。正常运行时仍应返回 401，避免攻击请求触发平台重试。清理资源
