3.8.5 上下文缓存
当应用在多轮对话、工具调用或固定提示词中反复发送相同的长前缀时，重复输入会持续消耗计算与成本。上下文缓存复用这些前缀的计算结果，隐式缓存对支持的模型自动启用，显式缓存由开发者主动开启并管理生命周期。两者不能同时生效，实际命中以缓存 Token 大于 0 为准，HTTP 200 或配置回显不能单独证明命中。若只调用一次且没有稳定重复前缀，通常不需要缓存。本文覆盖选型、接入、观测、计费与管理。
说明
方舟平台的新用户？获取 API Key 及 开通模型等准备工作，请参见 快速入门 。
快速开始
上下文缓存让支持的模型复用重复输入前缀。你不需要先选择模式，也不需要额外的缓存开关：第一轮请求预热缓存，第二轮保持相同长前缀、只替换末尾问题，对比两轮 usage 就能直接看到缓存收益。下面的示例使用 Responses API 的隐式缓存。
表中数值来自实际运行（ doubao-seed-2-1-pro-260915 ，固定前缀重复 30 次）；实际 Token 数取决于输入，速度收益取决于模型、前缀长度和服务负载。
cached_tokens 大于 0 表示本次命中；完整命中判定、零值排查和计费口径见 隐式缓存 > 观测与计费。

使用方式

缓存长度门槛
缓存创建：输入达到对应模型的门槛后，系统会自动缓存本次请求中可复用的前缀片段，不需要用户显式声明公共前缀。缓存创建后，后续请求的输入会自动与已有缓存匹配。
缓存命中：当后续请求的输入开头与已有缓存存在相同前缀时，系统会尝试复用对应的缓存结果，从而减少重复计算。 
不保证命中：缓存容量、淘汰策略、分布式路由、前缀稳定性和模型门槛都会影响实际命中，系统无法保证每次命中。
不保证最长前缀命中：系统会综合考虑可用资源与命中收益，命中长度可能不是全局最长命中的那一段。
输入达到对应模型的最小 Token 数后才会写入缓存，后续相同前缀才可能命中；低于门槛时能力仍然启用，只是本次不写入。不同模型的门槛如下：

优化缓存命中
建议按以下顺序使用：
准备稳定前缀：将稳定角色设定、背景知识、工具定义或长文本放在请求前部，将动态问题放在后部，并保持工具定义、工具顺序和结构化输出方案稳定。
发起请求：使用支持隐式缓存的模型。Chat、Responses 和 Messages 都会自动启用隐式缓存；Chat 和Responses 可选设置 prompt_cache_key 增强相同前缀请求的路由亲和，Messages 支持通过 metadata.user_id.session_id 传递会话标识实现缓存亲和，没有直接 prompt_cache_key 入参。Batch 对支持模型自动使用隐式缓存，但 cached_tokens 固定为 0，不能据此计算命中率。
验证命中：使用相同公共前缀发起有限次重复请求；完整判定步骤见 观测与计费 。
prompt_cache_key 配置
prompt_cache_key 用于提升相同前缀请求的路由亲和，不改变缓存是否启用。快速开始的 Chat 与Responses 示例已经包含该参数，可按以下约束设置：
会话隔离：上下文连续的请求使用同一取值；不同用户或并行会话使用不同取值。
流量控制：同一取值的总流量建议控制在每分钟 15 个请求以内；超过后部分请求可能回退到常规路由。

Session 缓存接入
Session 缓存按轮次续接，适合多轮对话和连续工具调用：
首轮开启：首轮设置 caching.type=enabled ，保持 store 实际为 true ，并保存响应返回的 id 。下一轮续接：下一轮设置 caching.type=enabled ，并通过 previous_response_id 传入紧邻上一轮的响应 id 。
连续轮次：后续每轮重复第 2 步；连续多轮请求之间建议加入约 100 毫秒延迟，间隔过短可能导致调用失败。
前置轮缺失：任一前置轮未写入缓存时，后续轮次无法补写该轮上下文；此时从仍有效的响应或新请求重新建立 Session 链。
Session 缓存原理
普通输入费用 = (input_tokens - cached_tokens) × 输入单价
缓存输入费用 = cached_tokens × 缓存输入单价
输出费用 = output_tokens × 输出单价
请求费用 = 普通输入费用 + 缓存输入费用 + 输出费用

未使用缓存：未使用 Session 缓存时，初始信息、前 N 轮对话和第 N+1 轮问题都需要重新计算并生成Tokens。

工作原理
客户端负责组织稳定前缀、保存响应 ID 并在后续请求中续接；方舟服务负责写入缓存、按前缀匹配并返回缓存 Token 用量。响应存储只是显式缓存的前提， store=true 不等于开启显式缓存；

隐式缓存没有单独的对比原理图；显式缓存的 Session 与 Prefix 详细原理图分别见 Session 缓存接入 和 Prefix 缓存接入 。本节只说明共同协作顺序。
阶段说明：
组织输入：客户端将稳定内容放在前部，将动态问题放在后部；Session 模式保留响应链，Prefix 模式准备固定前缀。
创建或写入：隐式缓存自动处理；显式缓存要求 caching.type=enabled 且 store 实际为 true ，并返回响应 ID。
复用与观测：隐式模式依赖输入中可复用的相同前缀，由系统自动匹配；显式模式在后续请求中保持 caching.type=enabled 并传入正确的 previous_response_id ，再通过缓存 Token 判断命中。终止：响应返回、缓存到期或删除、请求失败时结束当前链路。

命中：缓存 Token 大于 0，表示本次请求复用了部分缓存输入。

过期或删除：到期后不能继续引用旧响应 ID；删除中间轮后，后续内容会在下一次请求重新计算和存储。

常见问题
显式缓存和隐式缓存能否同时生效？
不能。请求使用显式缓存时，隐式缓存不生效；先按主动控制需求选择一种模式，再按该模式的字段和观测契约解释结果。
前缀缓存创建失败常见原因有哪些？
检查固定前缀是否达到 256 Tokens、创建请求是否错误设置 stream=true 、 caching.type 是否为 enabled 、 store 是否实际为 true ，以及 instructions 、 tools 、 json_schema 等组合限制。隐式缓存未传 prompt_cache_key 时是否仍会启用？
会。隐式缓存自动开启， prompt_cache_key 仅用于优化路由亲和，不是开关。
为什么隐式缓存请求成功但 cached_tokens 为 0？
检查输入是否达到对应模型门槛、公共前缀是否稳定，以及可选 prompt_cache_key 的 Endpoint、模型和取值是否保持一致；不要转而检查显式缓存字段。
为什么传入 previous_response_id 后显式缓存仍未命中？
确认首轮和每个后续请求都设置 caching.type=enabled ， store 实际为 true ， previous_response_id 对应正确的前缀创建 ID 或 Session 上一轮 ID，并检查缓存生命周期和版本切换窗口。判定口径见 命中与失效。
删除中间轮缓存后为什么费用上升？
