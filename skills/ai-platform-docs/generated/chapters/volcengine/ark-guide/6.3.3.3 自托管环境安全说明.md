6.3.3.3 自托管环境安全说明
本文介绍自托管环境（Self-hosted Environment）的安全责任模型、数据边界和最佳实践，帮助企业安全、平台和运维人员完成部署前安全评审。
安全责任模型
自托管环境采用共享责任模型：方舟负责控制面安全，企业负责执行面安全。
信任边界
自托管环境的信任边界位于方舟控制面与企业执行面之间：
方舟控制面：托管模型推理、Agent 编排、Session 管理和事件流。Tool Call 和 Tool Result 会经过控制面。
企业 Worker：部署在企业基础设施，轮询 Work Queue 并在企业 Sandbox 中执行工具。
企业 Sandbox：每个 Session 应使用独立的执行环境（容器、VM 或物理机上的隔离目录）。注意
自托管不等于"所有业务数据均不出域"。Tool Call 和 Tool Result 作为 Agent 推理的必要输入，会经过方舟控制面。如果你需要确保特定数据不进入方舟，应在工具实现中过滤敏感信息，或在Worker 侧对 Tool Result 进行脱敏处理。

凭证分离
业务应用和 Worker 当前都使用标准方舟 API Key。为缩小单个凭证的暴露面，建议分别分配独立 APIKey：
警告
Worker API Key 不是 Environment 专用凭证。 MA_ENVIRONMENT_ID 只用于定位 Work Queue，不会缩小 API Key 的授权范围。API Key 泄露后，攻击者可能访问该凭证有权操作的其他方舟资源。不要把任何 API Key 放入 Agent 工作目录、工具进程环境或日志。
凭证保存

Sandbox 隔离
每个 Session 应使用独立的执行环境，防止跨 Session 数据泄露和权限越界。
基本要求
每个 Session 使用独立的工作目录或 Sandbox
使用非 root 用户运行 Worker 和 Agent 工具
限制 CPU、内存、进程数和执行时间
不挂载以下目录到 Sandbox： 
Docker Socket（ /var/run/docker.sock ）
宿主机根目录（ / ）
凭证目录（如 /etc/ark/ 、 ~/.aws/ ）
其他 Session 的工作目录
常驻 Worker 模式
如果使用常驻 Worker（ EnvironmentWorker ），确保 Worker 的根工作目录只用于 Agent 执行，并让 SDK为每个 Session 创建独立子目录。需要扩容时，优先启动多个 Worker 进程或 Pod，并为每个实例设置独立的 MA_WORKER_ID 。
不要让多个 Worker 共享同一个 Session 工作目录，也不要把凭证目录、宿主机系统目录或其他业务目录作为 Worker 工作目录。
每 Session 独立 Sandbox 模式
推荐使用 Kubernetes 每 Session 一个 Pod，每个 Pod 拥有独立的文件系统、网络命名空间和资源限制。文件系统安全
Agent 通过 Bash 和文件工具访问企业文件系统，必须限制其可访问范围：
限制 Agent 可读写的根目录（如 /workspace ），禁止访问 /etc 、 /proc 、 /sys 等系统目录防止路径穿越：校验文件路径不包含 .. 或符号链接逃逸
限制文件类型和数量，防止 Agent 写入大量文件耗尽磁盘
自定义文件工具应重复执行路径校验，确保路径在允许范围内
任务结束后清理 Session 的临时数据
网络安全
自托管 Worker 仅需主动出站访问方舟 API，无需开放入站端口：
Worker 主机只需出站 HTTPS 访问 https://ark.cn-beijing.volces.com/api/v3
如果 Agent 需要访问企业内网服务，配置最小权限的域名或地址白名单
防止 Agent 通过代理或隧道访问未授权网络

工具执行安全
Worker 在企业侧执行 Agent 的工具调用，建议实施以下控制：
校验工具名称和输入参数 Schema，拒绝未定义的 Tool Call
对高风险工具（如数据库写入、生产环境部署）增加人工审批或二次确认
使用 Tool Call ID 保证幂等：服务端以 Tool Call ID 为幂等键，同一 Tool Call 的重复回传不会重复执行区分只读操作与写操作，对写操作实施更严格的权限控制
限制 Shell 命令：禁止 sudo 、 chmod 777 、 rm -rf / 等危险命令
清除包含凭证的环境变量后再执行 Agent 工具
注意
Tool Call ID 幂等由服务端保证，但 Worker 侧不应依赖此机制。如果 Worker 已经执行了有副作用的操作（如发送邮件、写入数据库），重复回传 Tool Result 不会撤销已有副作用。建议 Worker侧在本地记录已执行的 Tool Call ID，避免重复执行有副作用操作。

Worker 失联与任务接管
Heartbeat 机制
Worker 通过 Heartbeat 维持 Work Item 的租约。默认 TTL 为 300 秒，Worker 应在 TTL 过期前续租。租约回收
Worker 掉线超过租约 TTL 后，其他 Worker 可通过 Poll 时携带 reclaim_older_than_ms 参数接管失联的Work Item：
旧 Worker 恢复续租时，服务端返回 412 Precondition Failed，表示租约已被接管
旧 Worker 应停止当前执行并退出，避免与新 Worker 并发执行
注意
两个 Worker 并发执行同一个 Work Item 可能导致工具重复执行。Worker 应在每次 Heartbeat 成功后检查 lease_extended 字段，若为 false 则立即停止执行。
迟到 Tool Result
Work Item 进入 stopped 状态后，发送新的 Tool Result 会使 Work Item 重新进入 queued 状态，并继续驱动 Session。Session 进入 terminated 状态后不再接受 Tool Result，请求返回 403 
OperationDenied.SessionTerminated 。
上线前检查清单
部署自托管环境前，逐项确认以下安全检查项：
业务应用与 Worker 分别使用独立 API Key
Worker API Key 的账号和项目权限已纳入安全评审，未假设其仅能访问单个 Environment
API Key 保存在 Secret Manager，未写入代码仓库、镜像、工作目录或日志
每个 Session 使用独立的工作目录或 Sandbox
Agent 以非 root 用户运行
文件系统访问限制在允许范围内，防止路径穿越
网络访问配置最小权限，不开放入站端口
工具输入经过 Schema 校验，拒绝未定义的 Tool Call
高风险工具有审批或二次确认机制
Tool Call 幂等处理已实现，避免重复执行有副作用操作
日志已脱敏，不包含完整凭证和敏感数据
Worker 支持优雅退出，收到停止信号后清理执行环境
已完成 Worker 失联和租约回收的异常演练
安全边界
使用自托管环境时，需要明确以下安全边界：
方舟控制面不校验企业 Sandbox 的隔离程度，隔离责任完全在企业侧
方舟不监控企业 Worker 主机的安全状态（如系统漏洞、异常进程）
Tool Permission 等待期间，Worker 需持续维持 Heartbeat 等待用户审批
不支持企业自定义的审计日志格式和投递目标
