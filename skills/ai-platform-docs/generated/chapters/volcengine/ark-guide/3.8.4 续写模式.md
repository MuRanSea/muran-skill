限制与不支持项
模型不支持：支持表之外的其他深度思考模型以 assistant 消息结尾时， thinking 字段失效，模型保持默认思考行为。改用支持续写的模型，并按 支持模型 选择配置。
取值不支持：只设置 prefix=true ，但没有把最后一条消息设为 assistant 或 content 为空，请求不满足续写配置。应同时把最后一条消息设为 assistant 并填写非空 content 。
组合不支持：把续写当作严格结构化输出，或无上限循环生成超长内容，可能导致格式不稳定或产生意外 Token 用量。应校验格式，并为多轮任务设置完成条件和最大轮数。
字段失效：在支持表之外的深度思考模型中设置 thinking ，该字段会失效并保持模型默认思考行为。先核对模型范围，不要因为请求以 assistant 消息结尾，就认为该模型一定支持续写。
Messages API 模型差异：Messages API 不需要额外开关，但 assistant 预填是否生效取决于模型。DeepSeek V4.1 Flash 系列与 GLM-5.3 Flash 会忽略预填并返回完整回答；未验证模型不要依赖。场景边界：续写无法保证 JSON/XML 等严格语法，下游解析可能失败。需要严格格式时使用结构化输出，并保留客户端校验。

为什么返回内容里没有预填的等号或左花括号？
接口只返回预填之后的新生成片段；完整判断与处理动作见 检查返回结果与停止条件 。
预填左花括号能否保证得到合法 JSON？
不能。它只引导输出开头；应执行 JSON 校验，或改用 结构化输出 。
当前模型在不同 API 下需要额外设置吗？
先查 支持模型 。Chat API 中只有部分模型需要 prefix=true ；Responses API 所有模型都要 partial=true ；Messages API 不需要额外开关，但 assistant 预填是否生效取决于模型：豆包与 Kimi 可续写，DeepSeek V4.1 Flash 与 GLM 不生效。
用续写生成超长内容时怎样避免意外花费？
为循环设置最大次数和业务完成条件，逐轮检查 usage ，达到任一条件即停止。配置方式见 典型场景。
